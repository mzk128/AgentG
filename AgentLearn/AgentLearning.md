#### 记忆机制/记忆系统

- Agent系统通常会设计短期记忆和长期记忆两层，短期记忆为**当前任务**执行过程中的中间状态，存在**上下文**里；长期记忆是**跨任务**的，存储在**向量数据库**中。
- 类似与存储器
- 针对**短期记忆**，存储在context window里，容量有限，任务结束后便清空。短期记忆遇到的最大问题为上下文窗口有限，解决办法有**摘要压缩**或**滑动窗口**，不管哪种方式，都会丢失信息
- 针对**长期记忆**，存储在向量数据库里，Agent系统里面实现方式通常为向量检索+metadata过滤。长期记忆的问题是`什么该存，什么不该存`以及`存储之后如何管理`。长期记忆中有一个重要机制`记忆衰减（Memory Decay）`

#### 多步推理与自我纠错/规划模块

- 两种推理技术：**CoT（Chain of Thought，思维链）**、**ToT（Tree of Thoughts，思维树）**
- 三种主流模式（设计范式）：Plan-and-Execute（先规划后执行）、ReAct（边执行边规划）、Reflection（反思）

##### 推理技术

- CoT，Chain of Thought，思维链
  - Zero-shot CoT，直接在`prompt`末尾加上`让我们一步步思考`。零成本、格式不稳定，推理步骤长短、风格不一
  - Few-shot CoT，需要在`prompt`里给几个带有完整推理过程的例子，让 LLM 照着这个格式来模仿。效果更稳定、可控性更强，缺点是占用更多token

##### 设计范式/推理模式

- ReAct（Reasoning + Acting），`走一步看一步`，每一轮/每一步都是由三个步骤组成，形成一个完整的`Thought->Action->Observation`循环。缺点是，每一步都是局部最优决策，处理复杂的需要全局规划的任务时，容易在中间迷失方向

  - 针对`ReAct`推理模式，LLM每次只做一件事情，根据当前的历史（记忆系统），输出下一步的`Thought + Action`，框架负责的事情：管理对话历史、执行工具、检测循环终止条件

  - 缺点：**循环漂移**，步骤越长，历史上下文越长，这种漂移的概率就越大；**错误传播**，ReAct的每一步决策都建立在前面所有步骤的结果之上，如果中间某一步拿到了错误的信息，或者工具返回了一个有误的结果，后面所有的推理都会被这个错误带跑。

    两个缺点出现的根源是同一个：ReAct是纯粹的**前向推理**，没有`全局规划`约束方向，也没有`反思机制`来纠正错误

- Plan-and-Execute，将`规划`与`行动`解耦。在执行任务之前，先让LLM专门做规划，输出完整的步骤列表，然后由另外的LLM逐步执行。这其中有一个非常重要的机制`动态重规划`，计划是活的，会根据执行结果动态调整。缺点为多了规划和重规划的LLM调用，延迟和成本都会增加

  - 第一阶段是`规划`；第二阶段是`执行`，按照顺序一步一步地执行，每一步的执行本身可以用`ReAct`模式来跑
  - 其中关键的设计为`动态重规划（动态Replan）`，每执行完一步，系统都会检查一下：这一步的实际结果和预期是否一致？

- Reflection（反思），Agent完成一步或者完成整个任务之后，再让一个LLM来判断做得好不好、结果是否符合预期

  - Reflection不是一套独立的完整流程，而是给ReAct、Plan-and-Execute加的`buff`，在原本做事流程的基础上，加上一层`自我检查、自我修正`的环节
  - 进阶机制：`Reflexion`，不仅检查输出对不对，还会把每次失败的原因总结成一段`经验教训`，存进记忆里，下次再遇到类似任务时，这段教训会作为上下文传给 LLM，让它避免重蹈覆辙。


实际项目里三种范式不是互斥的，很多系统会混合使用，比如用`Plan-and-Execute`进行整体规划，每个步骤内容使用`ReAct`执行，关键步骤再加上`Reflection`进行质量把关

实际工程里，纯Agent模式其实不多，因为太难控制，更常见的是`Agentic Workflow`

##### 任务拆分

- 静态拆分，提前把任务流程设计好，固定成一个确定的workflow，每一步是什么，按照什么顺序进行，全部事先写死
- 动态拆分，把`任务拆解`交给LLM，你给它一个目标，让它先输出一个执行计划，再按计划一步步执行
- 验证标准：完备性、独立性、可验证性

### Agent与Workflow

核心区别：在于谁去做`下一步去哪`决策，对于Agent，LLM符合做出决策；对于Workflow，决策为开发者在代码中写死，LLM负责**意图识别**和**生成回答**。

#### Agentic Workflow

- 生产环境中最主流的模式，Agentic Workflow，关键在`Agent`与`Workflow`之间做出平衡性的选择
- 用**Workflow**固定主流程的骨架，在需要灵活判断的节点嵌入Agent，其余固定节点直接用LLM或Tools
- 骨架是确定的，让开发者可以控制整体行为；关键节点放置Agent，可以应对复杂情况
- 五种编排模式：Prompt Chaining（提示链式）、Routing（路由选择）、Parallelization（并行化）、Orchestrator-Workers（协调者-工作者）、Evaluator-Optimizer（评估者-优化器）

Anthropic观点，能用`Workflow`解决的问题，就不要用`Agent`。先从最简单的Workflow开始，只有当发现某个节点确实需要灵活决策、写死的逻辑无法覆盖所有情况时，才把那个节点升级为Agent，`从简单到复杂、按需升级`

### Multi-Agent

Multi-Agent（多智能体系统）是多个`Agent`协作完成任务，每个Agent各有分工，有的负责搜索、有的负责写代码、有的负责做评审。

单个Agent主要有两个限制，一是上下文，即context window的大小，复杂任务信息量一多就撑爆；二是单点能力，什么都让一个Agent做，每件事情都是泛才。

Multi-Agent 通过`专业分工`和`并行执行`，能处理更复杂、更长流程的任务。

主流 Multi-Agent 设计的趋势，用确定性工作流控制边界，用 LLM 做规划与动态选择，用专业子 Agent 执行，并通过结构化状态、并行调度、审查和明确终止条件保证可靠性

#### 主流模式

- Supervisor / Manager，中央 Agent 调用专业 Agent，并汇总最终答案
- Router，分类后路由到一个或多个专业 Agent
- Orchestrator–Worker，编排者动态拆分任务，生成多个 Worker
- Handoff / Swarm，当前 Agent 把控制权移交给另一个 Agent
- Selector Group Chat，模型根据共享对话选择下一发言者
- Debate / Voting，多个 Agent 独立判断、互评或投票
- A2A 分布式协作，独立 Agent 服务通过标准协议发现和委派
