# Agent 学习笔记审阅与补充

> 审阅对象：`AgentLearning.md`  
> 审阅日期：2026-09-04  
> 说明：本文用于纠错和补充，不修改原学习笔记。协议类内容会持续演进，文中涉及 MCP、A2A 版本时应以官方最新规范为准。

## 一、总体结论

原笔记已经抓住了 Agent 学习的几条主线：工具、记忆、规划与反思、Agent/Workflow 的差异，以及 MCP/A2A 协议。但目前仍像一份提纲，主要问题有三类：

1. **定义过窄**：把 LLM 说成问答机器，把长期记忆等同于向量数据库。
2. **绝对化表述**：例如“ReAct 每一步都是局部最优”“Plan-and-Execute 必须由另一个 LLM 执行”“Workflow 的决策全部写死”。
3. **关键工程知识缺失**：工具调用闭环、状态与记忆的区别、终止条件、可靠性、安全、可观测性、评测，以及 A2A 的核心对象尚未展开。

建议把 Agent 理解为一个**受约束的闭环软件系统**，而不只是“会思考、会调用工具的 LLM”：

```text
用户目标
   ↓
上下文构建 → 模型决策 → 结构化动作 → 权限/参数校验 → 环境或工具执行
   ↑                                                   ↓
状态更新 ← 记忆读写 ← 结果验证/错误处理 ←─────────────── 观察结果
   │
   └── 达成目标 / 超出预算 / 需要人工输入 / 无法继续 → 结束
```

模型是决策组件之一；真正的 Agent 还需要运行时、工具、状态、控制流、权限边界和验证机制。

## 二、原笔记逐项纠错

| 原笔记位置 | 判断 | 更准确的说法 |
| --- | --- | --- |
| 第 3 行：“LLM 本质上是一个问答机器” | **不准确** | LLM 本质上是根据上下文建模并生成 token 的模型，可完成生成、抽取、分类、转换、推理等任务。“问答”只是应用形态。LLM 单独调用通常没有持久目标、环境反馈闭环和真实行动能力；Agent 则把模型置于可观察、可行动、可迭代的运行时中。 |
| 第 5 行：“特别的 Agent” | **疑似标题笔误** | 结合下文，更像是“Agent 的核心组成”。常见组成包括模型、指令、工具、状态/记忆、编排运行时、验证/护栏和人工介入点。 |
| 第 13～16 行：短期/长期两层记忆 | **可作入门模型，但不完整** | 短期与长期是按时间跨度划分的一种方式，不是唯一分类。还可按功能分为工作记忆、情景记忆、语义记忆、程序性记忆；按载体分为上下文内、外部存储、参数化记忆等。 |
| 第 13、16 行：“长期记忆存储在向量数据库” | **过度绝对** | 向量库适合语义相似检索，但长期记忆也可放在关系数据库、键值存储、文档库、知识图谱、文件或混合索引中。结构化事实、精确 ID、时间范围查询往往不适合仅靠向量相似度。 |
| 第 15 行：“短期记忆在任务结束后清空” | **不一定** | 对话上下文会受窗口限制，但任务状态可以通过 checkpointer、数据库或事件日志持久化，从而暂停、恢复甚至跨进程继续。应区分“模型本次看到的上下文”和“系统保存的状态”。 |
| 第 15 行：“摘要或滑窗都会丢失信息” | **方向对，但需限定** | 摘要是有损压缩，滑窗会让窗口内看不到被移出的内容；但原始事件可继续保存在外部存储，需要时再检索，因此不等于系统永久删除了信息。 |
| 第 16 行：“记忆衰减是重要机制” | **不是必选机制** | 衰减只是遗忘策略之一。更完整的生命周期是：写入判定、去重、关联、检索、更新、冲突解决、压缩、过期/删除、权限和审计。某些关键事实反而不能随时间自然衰减。 |
| 第 20 行：“两种推理技术” | **不完整** | CoT、ToT 是代表性方法，不是仅有的两种。还包括任务分解、自一致性采样、搜索、规划、程序辅助推理、检索增强、基于验证器的迭代等。它们也不是 Agent 专属能力。 |
| 第 26 行：Zero-shot CoT“零成本” | **错误** | 它只是无需人工准备 few-shot 示例，并非没有成本；额外推理仍消耗 token、时间和费用。“让我们一步步思考”是经典触发语，不是稳定保证，也不应让系统依赖模型输出完整的内部思维过程。工程上更应要求简洁依据、结构化计划和可验证中间结果。 |
| 第 27 行：Few-shot CoT“效果更稳定” | **有条件成立** | 示例能约束任务格式，但示例质量、任务匹配度、模型能力和上下文长度都会影响效果；错误示例还会造成误导。它不是必然优于 zero-shot。 |
| 第 31 行：ReAct“每一步都是 Thought → Action → Observation” | **是经典抽象，不是硬性接口** | 论文核心是交错进行推理与行动。工程实现中，一轮可能产生工具调用、直接答复、计划更新或请求人工输入；推理也可能由模型内部完成，不一定以可见 `Thought` 暴露。 |
| 第 31 行：ReAct“每一步都是局部最优决策” | **错误** | ReAct 没有定义或保证“最优”。模型只是基于当前上下文选择下一动作。它可以维护和调整高层计划，但默认没有系统性的多分支搜索、最优性证明或可靠回溯。 |
| 第 37 行：ReAct 是“纯前向推理、没有全局规划和纠错” | **过度绝对** | 原始 ReAct 就允许跟踪、更新计划和处理异常。更准确的局限是：单轨迹执行容易受错误观察、上下文增长和停止判断影响；若没有外加验证器、分支搜索或检查点，回溯纠错能力通常较弱。 |
| 第 39 行：Plan-and-Execute“由另外的 LLM 逐步执行” | **不是必要条件** | Planner 和 Executor 可以使用不同模型、同一模型的不同提示，也可以由确定性代码执行某些步骤。关键是职责和阶段解耦，而不是模型实例必须不同。 |
| 第 39、42 行：“动态重规划”“每执行完一步都会检查” | **常见增强，不是定义要求** | 基础 Plan-and-Execute 可以只生成一次计划。重规划可按每步、失败、状态显著变化或固定检查点触发；触发过频会增加成本，过少则降低适应性。 |
| 第 44～47 行：Reflection 与 Reflexion | **大体正确，需分层** | Reflection 是通用的评审/改进机制，可由同一模型、另一个模型、规则、测试或人完成。Reflexion 是特定研究框架：把反馈转成语言反思并放入情景记忆，在后续尝试中复用，不通过更新模型权重来学习。 |
| 第 52、77 行：“生产环境更主流/最主流” | **缺少可验证依据** | 更稳妥的表述是：确定性流程与有限 Agent 节点混合，是常见且实用的工程选择，因为它通常更易测试、审计和控制；是否“主流”取决于领域和统计口径。 |
| 第 56 行：静态拆分“全部写死” | **过窄** | 预定义 Workflow 也可以包含条件分支、循环、并行、失败转移，甚至用 LLM 做分类路由。其关键是可选路径和边界由代码预先限定，而不是所有步骤永远线性不变。 |
| 第 64～65 行：MCP 管理 Agent 与工具的连接 | **不完整** | MCP 标准化的是 LLM 应用与外部上下文/能力的集成。Server 可暴露 `resources`、`prompts`、`tools`；它不是 Agent 编排框架，也不负责决定 Agent 下一步做什么。 |
| 第 73 行：Agent 与 Workflow 的区别 | **核心方向正确，但二分过强且有“符合/负责”笔误** | 更准确的区分是：Workflow 的执行路径由预定义代码控制；Agent 由模型动态决定过程和工具使用。二者是连续谱，可以嵌套组合。Workflow 中的 LLM 不只负责意图识别和回答，也可抽取、生成、评分或路由。 |

## 三、需要补充的核心知识

### 1. LLM、Agent、Workflow 与 Agentic System

| 概念 | 控制权 | 是否主动作用于环境 | 典型用途 |
| --- | --- | --- | --- |
| LLM 调用 | 调用方给定输入，模型生成输出 | 通常不能；工具请求仍需宿主执行 | 总结、分类、生成、抽取、问答 |
| Workflow | 代码预定义允许的路径和转换 | 可以，通过固定节点调用工具 | 稳定、可预测、规则明确的业务流程 |
| Agent | 模型在约束内动态选择下一动作 | 可以，通过工具形成观察—行动闭环 | 路径难预先枚举、需要适应环境的任务 |
| Agentic System | Workflow、Agent、工具和人机协作的总称 | 视设计而定 | 真实应用通常属于这一层 |

一个实用的 Agent 最小定义可以写成：

```text
Agent = Model + Instructions + Tools + State + Control Loop + Guardrails
```

是否称为 Agent，不应只看“有没有调用 LLM”，而应看模型是否对任务过程具有一定动态控制权。

### 2. Agent 的运行闭环与状态机

最小闭环一般包括：

1. 接收目标，判断信息是否充分。
2. 构建本轮上下文，包括指令、当前状态、必要记忆和可用工具。
3. 模型选择动作：回答、调用工具、更新计划、请求输入或结束。
4. 运行时校验动作的结构、参数、权限与风险。
5. 执行动作，获得可信度不同的观察结果。
6. 更新状态并验证进展，必要时重试、改道、回滚或升级给人。
7. 命中成功或停止条件后输出结果。

状态最好显式建模，而不是把全部信息塞进聊天记录。例如：

```python
state = {
    "goal": "用户目标",
    "plan": [],
    "completed_steps": [],
    "artifacts": [],
    "evidence": [],
    "errors": [],
    "attempts": 0,
    "budget": {"max_steps": 12, "max_cost": 1.0},
    "status": "running",
}
```

显式状态有利于持久化、恢复、测试、前端展示和故障定位。

### 3. 工具调用不是“模型直接执行函数”

一个完整的工具调用链路是：

```text
工具名、说明、参数 Schema
        ↓
模型生成结构化调用请求
        ↓
宿主校验名称、参数、权限、预算、用户授权
        ↓
真正的执行器调用 API / 数据库 / 文件系统 / 浏览器
        ↓
标准化结果或错误写回上下文
        ↓
模型根据观察决定下一步
```

模型发出的只是**调用意图**，真正执行动作的是 Agent 宿主或运行时。工程上还要处理：

- 工具描述清晰且边界单一，参数使用严格 Schema。
- 超时、限流、重试、熔断和错误分类。
- 对有副作用的操作使用幂等键；区分可安全重试和不可重复执行的动作。
- 查询和写入分权；删除、付款、发送消息、发布内容等高风险动作应设置审批点。
- 工具结果和网页内容均视为不可信数据，防止间接提示注入。
- 限制返回体大小，保留来源、时间、状态码等 provenance（来源信息）。

工具越多不一定越好。大量含义相近的工具会增加选择错误；应优先改善命名、描述、Schema、示例和错误反馈。

### 4. Context、State、Memory 与 RAG 的区别

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| Context | 某一次模型调用当前可见的全部输入 | 系统指令、最近消息、工具结果、检索片段 |
| State | 工作流在某一时刻的结构化事实 | 当前步骤、尝试次数、任务状态、产物路径 |
| Memory | 为未来决策保留并可选择性取回的信息 | 用户偏好、过去失败经验、历史任务事实 |
| RAG | 从外部知识源检索内容来增强当前生成 | 从产品文档中找与问题相关的段落 |

RAG 是一种“取知识”的机制，但检索到的公共文档不必然是 Agent 的记忆；只有当系统保存并复用与交互、用户或历史经历有关的信息时，才更接近 Agent memory。

记忆系统应设计完整的读写闭环：

```text
候选信息 → 是否值得写 → 规范化/去重 → 存储与权限
                                       ↓
当前任务 ← 排序/过滤/重排 ← 检索召回 ← 查询构造
   ↓
使用反馈 → 更新、合并、纠错、过期或删除
```

常见失败包括错误记忆被长期放大、旧事实覆盖新事实、相似但无关内容被召回、不同用户数据串线，以及敏感信息无法删除。应记录来源和时间，支持作用域隔离、冲突解决、用户查看/修正/删除，并对写入和检索分别评测。

### 5. 推理、规划与验证应分开理解

- **CoT**：顺序产生中间推理步骤的提示方法。适合线性可分解问题，但中间步骤也可能自信地出错。
- **Self-consistency**：对同一问题采样多条候选推理，通过投票或验证选择结果；以额外成本换取稳健性。
- **ToT**：把候选“思路”组织为搜索树，包含生成、评分、剪枝和回溯；它不仅是“更长的 CoT”。
- **ReAct**：让推理与环境行动交错，通过真实观察更新决策。
- **Plan-and-Execute**：先形成全局计划，再执行步骤，并可按策略重规划。
- **Reflection**：对结果或轨迹进行复核和改进；验证来源可以是模型、规则、测试、外部事实或人。
- **Reflexion**：把反馈语言化并保存在情景记忆中，供后续尝试参考，不更新模型权重。

关键原则是：**生成器与验证器最好职责分离，能用确定性验证就不要只靠 LLM 自评。** 例如代码用测试和静态检查，计算用程序重算，结构用 Schema 校验，事实用来源交叉核验。LLM Judge 适合评价风格、相关性等开放指标，但也需要标定、盲评和抽样人工复核。

### 6. Workflow 模式的适用条件

| 模式 | 核心结构 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| Prompt Chaining | A → B → C | 可稳定拆成固定阶段 | 延迟叠加、前序错误传播 |
| Routing | 分类 → 专用分支 | 输入类别边界清楚 | 错误路由、边界样本 |
| Parallelization | Fan-out → 聚合 | 独立子任务或多视角评审 | 写冲突、重复成本、聚合困难 |
| Orchestrator-Workers | 动态拆分 → 委派 → 汇总 | 子任务数量和类型事前未知 | 协调开销、遗漏、重复劳动 |
| Evaluator-Optimizer | 生成 ↔ 反馈迭代 | 有清晰质量标准且迭代确有收益 | 无休止修改、评估器偏差 |

并行化前应确认子任务独立、共享状态不会发生写冲突，并预先定义合并策略。Evaluator-Optimizer 必须设置通过标准和最大轮数。

### 7. 多 Agent 系统

多 Agent 的价值不是简单地“多调用几个模型”，而是隔离上下文、权限、职责或并行工作。常见拓扑包括：

- **Supervisor/Workers**：主管分配任务并汇总。
- **Handoff**：当前 Agent 将控制权和必要上下文转交给更合适的 Agent。
- **Peer/Swarm**：多个对等 Agent 协商或竞争，灵活但更难约束。
- **Blackboard**：Agent 通过共享结构化状态协作。
- **Generator/Critic**：生成与审查分工。

只有出现以下情况时，多 Agent 才更可能值得：需要明显不同的专业上下文或工具权限、子任务确实可并行、单 Agent 上下文过载，或独立评审能显著提高质量。否则它通常只会增加 token、延迟、状态同步、重复工作和故障面。

多 Agent 交接至少要包含：目标、已完成工作、证据/产物、约束、剩余任务、失败历史、权限和完成标准。不要无边界地转交完整聊天记录。

### 8. MCP 与 A2A

#### MCP（Model Context Protocol）

MCP 解决的是 LLM 应用如何以统一协议连接外部上下文和能力。当前官方规范采用 Host—Client—Server 角色：

- **Host**：面向用户的 LLM 应用，负责模型集成、权限、用户同意、上下文聚合和整体编排。
- **Client**：由 Host 管理的协议连接器；一个 Client 与一个 Server 通信。
- **Server**：提供聚焦的外部能力，可暴露 `resources`、`prompts` 和 `tools`。

当前（2026-07-28）规范使用 JSON-RPC 2.0、自包含的无状态请求和逐请求能力声明，并支持进度、取消、错误报告等机制；长期任务等能力可作为扩展协商。旧版本资料可能描述初始化会话等不同细节，学习时必须注明协议版本。

MCP 不等于普通 function calling：function calling 是模型/平台生成结构化工具请求的能力；MCP 是应用和外部能力提供方之间的互操作协议。也不是所有工具都必须通过 MCP 暴露。

#### A2A（Agent2Agent Protocol）

A2A 面向的是相互独立、通常远程部署的 Agent/Agentic System 之间的互操作。调用方不需要知道远程 Agent 内部用了什么模型、工具或记忆。

核心对象包括：

- **Agent Card**：描述 Agent 身份、服务地址、能力、skills 和认证要求的 JSON 元数据。
- **Message / Part**：一次通信及其中的文本、文件引用、二进制或结构化数据片段。
- **Task**：带唯一 ID 和生命周期的有状态工作单元，适合长任务和多轮协作。
- **Artifact**：任务生成的可交付结果，如文档、图片或结构化数据。
- **Context**：用 `contextId` 关联一组相关 Task。

A2A 支持普通请求/响应、轮询、SSE 流式更新和异步推送通知。认证信息通常通过 HTTP 头传递，不应把明文密钥写进 Agent Card 或消息正文。

#### 三者不要混淆

| 机制 | 主要连接对象 | 解决的问题 |
| --- | --- | --- |
| Function/Tool Calling | 模型 ↔ 宿主定义的函数接口 | 让模型产生结构化动作意图 |
| MCP | LLM 应用 ↔ 外部上下文/能力服务 | 标准化发现和调用资源、提示与工具 |
| A2A | Client Agent ↔ Remote Agent | 标准化 Agent 发现、消息、长任务状态和产物交换 |

一个远程 Agent 可以通过 A2A 对外协作，同时在内部通过 MCP 使用工具；二者互补而不是替代关系。

### 9. 可靠性、安全与人工介入

Agent 拥有行动能力后，安全问题会从“回答可能不准”升级为“可能执行错误动作”。最低限度应考虑：

- **停止条件**：成功、失败、最大步数、最大时间、最大 token/费用、重复动作检测。
- **失败策略**：区分瞬时错误、参数错误、权限错误和业务错误；限制重试并保留失败证据。
- **最小权限**：按 Agent、工具、资源和操作类型授权；读写分离，默认拒绝越权。
- **人机协作**：高风险或不可逆动作执行前审批；目标/偏好不明确时请求用户判断。
- **提示注入防护**：外部内容只能作为数据，不能覆盖系统指令；敏感数据和工具结果按信任域隔离。
- **沙箱与密钥**：不把秘密放入 prompt；代码执行、文件和网络访问放入最小权限沙箱。
- **可恢复性**：检查点、幂等、补偿操作和审计日志。回滚并不总是可行，因此应优先阻止错误副作用。

“模型更聪明”“降低 temperature”“加一句请仔细检查”都不能替代这些系统控制。

### 10. 可观测性与评测

至少记录以下轨迹：模型/提示版本、输入摘要、状态转换、工具名称与参数（脱敏后）、工具结果、错误、延迟、token/费用、审批记录和最终产物。日志需要 trace/task ID 关联，但不应泄露思维链或敏感数据。

评测不要只看最终回答的主观观感，可分四层：

1. **组件级**：路由准确率、检索 Recall@K、工具参数正确率、记忆写入/召回质量。
2. **轨迹级**：是否选择正确工具、是否重复循环、步骤数、恢复失败的能力。
3. **任务级**：端到端成功率、完成质量、事实依据、人工接管率。
4. **系统级**：P50/P95 延迟、token/费用、异常率、安全违规率、并发稳定性。

建立固定测试集和失败样本集，使用 mock 隔离外部依赖，并在模型、prompt、工具 Schema 或工作流变更后做回归测试。对于开放式质量，可以结合确定性检查、LLM Judge 和人工抽检，避免只依赖单一评估器。

## 四、推荐的学习与实践顺序

1. 先实现单次 LLM 调用和结构化输出，理解 token、上下文窗口与 Schema。
2. 实现一个只读工具，走通“请求—校验—执行—观察—回答”闭环。
3. 增加显式状态、停止条件、超时、错误分类和有限重试。
4. 用预定义 Workflow 完成 Prompt Chaining、Routing 和 Evaluator-Optimizer。
5. 实现一个有预算限制的 ReAct Agent，并为工具选择和终止行为写测试。
6. 增加 checkpoint，再区分短期状态、长期记忆和 RAG 知识库。
7. 加入权限审批、提示注入测试、日志、trace 和端到端评测。
8. 单 Agent 无法满足明确需求时，再尝试 Planner/Executor/Reviewer 或 Supervisor/Workers。
9. 最后学习 MCP 与 A2A；先理解它们解决的互操作问题，再选择 SDK。

每次增加复杂度时，都应比较它是否真的提高任务成功率，以及为此付出的延迟、费用和故障面。

## 六、一句话复盘

学习 Agent 的重点不应停在提示词或“让模型多思考”，而应转向：**如何让一个概率模型在有限权限、显式状态、可靠工具、可验证反馈和明确预算中完成闭环任务。**
